# Session 2026-08-25 10:42

> When to read: vor dem Wipe am Messetag, bei Arbeit an `bin/` (Health-Check,

## Kontext

Tag vor Messebeginn. Ausgangsfrage des Users: einen Monat auf Supabase Pro
upgraden, um ein Fallback zu haben? Daraus wurde die Erkenntnis, dass Pro das
gewünschte Problem gar nicht löst — und anschliessend das Tooling, das es
tatsächlich löst.

## Was passiert ist

**Pro-Frage beantwortet (Recherche statt Gedächtnis):**

- **PITR ist nicht Teil von Pro**, sondern ein separates, nutzungsbasiert
  abgerechnetes Add-on. Die bestehende ADR 2026-08-24 führt „kein PITR" als
  Free-Nachteil — ein Pro-Upgrade hätte das *nicht* behoben.
- Pro allein gibt tägliche Snapshots (7 Tage Retention). Für einen einzelnen
  Messetag wertlos: der jüngste Snapshot stammt von vor Messebeginn, ein
  Restore läge also vor allen Votes des Tages.
- Verbleibendes echtes Argument war E-Mail-Support — ohne Same-Hour-SLA für
  einen 8-Stunden-Einsatz aber nicht entscheidend.
- Asymmetrie als Kernpunkt: Support/Ressourcen sind reaktiv nachkaufbar, ein
  Backup nicht — das existiert nur, wenn der Plan vor dem Verlust aktiv war.

**Tooling gebaut** (`bin/`, dependency-frei, ~730 Zeilen inkl. Tests):

- `npm run health` — `.env`, Supabase-REST (Status/Latenz), Zeilen-Count und
  letzter Vote, `submit-vote`-Erreichbarkeit. Read-only, Exit 0/1.
  `--origin=` macht daraus einen echten CORS-Preflight.
- `npm run snapshot [-- --label=… --page-size=…]` — CSV-Export nach `backups/`.
  Serverseitiger Count vorher, Abgleich nachher: zu wenige Zeilen → Abbruch
  **ohne Datei**. Paginierung mit festem `order=created_at.asc,id.asc`,
  Duplikat-Check auf IDs, Schreiben mit Flag `wx` (nie überschreiben).
- Logik in `bin/lib/`, 28 Unit-Tests. Suite gesamt: 85 grün.

**Vorab verifiziert statt angenommen:** `anon` darf `votes` lesen (Policy
`allow select` `USING true` + `SELECT`-Grant) — also kein Service-Role-Key und
kein neues Secret nötig.

**Probelauf mit 9 Votes über die echte App**, danach Wipe via `service_role`,
Count zurück auf 0, beide Probelauf-CSVs gelöscht. Details in `docs/todos.md`
unter `## Erledigt`.

## Entscheidungen

- **Kein Pro-Upgrade** — ADR 2026-08-24 bestätigt, aber aus einem neuen Grund:
  Pro löst das benannte Problem gar nicht. Vorschlag, das als Ergänzung in die
  bestehende ADR zu heben (siehe Offene Punkte).
- **Der echte Fallback ist bereits gebaut** — die Offline-Queue auf den iPads
  schützt bei Backend-Ausfall besser als jede Plan-Stufe. Kein Handlungsbedarf.
- **Snapshot vor jedem `DELETE` wird Werkzeug statt Disziplin.** Das Skript
  bricht lieber ab, als still gekürzt zu schreiben — ein unvollständiges Backup
  wäre schlimmer als keins, weil es Sicherheit vortäuscht.
- **`--page-size` ist Probelauf-Hilfe, kein Tuning-Regler.** Grund: Unit-Tests
  prüfen die Paginierung gegen einen Fake-Pager, also gegen die eigene Annahme
  über PostgREST. Nur ein echter Mehrseiten-Lauf schliesst diese Lücke — er lief
  und lieferte eine byte-identische Datei zum einseitigen Export.
- **Keine Grant-Änderung am Vortag.** Der `TRUNCATE`-Befund wird bewusst erst
  nach der Messe angefasst.

## Offene Punkte

- **Messetag:** Snapshot vor Türöffnung → `DELETE` → Count-Check; nach

- **Abstimmen:** ADR 2026-08-24 um den PITR-Befund ergänzen? Die ADR liest sich
  aktuell so, als hätte Pro PITR gebracht. Ohne Korrektur wird die Frage in einer
  späteren Session auf derselben falschen Grundlage neu gestellt.
- **Nach der Messe:** `REVOKE TRUNCATE ON public.votes FROM anon;` — `anon` hat
  kein INSERT/UPDATE/DELETE, aber TRUNCATE, und RLS greift dort nicht. Über
  PostgREST nicht erreichbar, also kein akutes Risiko.
- **1 Commit unpushed** (`7da6adda`). Das Tooling selbst ist bereits auf
